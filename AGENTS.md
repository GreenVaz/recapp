# Правила для coding agents

Цей файл читають Claude Code, Codex та інші агенти перед роботою з
репозиторієм. Він описує не стиль коду, а **рішення, які легко зламати,
не помітивши цього**.

---

## 1. Межі, які не можна переходити

### Гроші — цілі мінорні одиниці, ніколи не float

У всьому TypeScript-коді сума — це `number` у копійках (`1500000` = 15 000,00).
У PostgreSQL — `NUMERIC(18,2)`. Перетворення живе рівно в двох місцях:
`src/core/money.ts` і `api/_lib/mappers.ts`.

Не вводьте дробові суми в бізнес-логіку. `0.1 + 0.2 !== 0.3`, і на сотні
операцій похибка стає видимою в балансі.

### Дати — рядки `YYYY-MM-DD`, ніколи не `Date`

`src/core/dates.ts` працює з рядками. `Date` завжди несе час і часовий
пояс: «5 листопада» в Києві та в UTC — різні моменти, і платіж з'їжджає на
добу при перетині півночі або зміні поясу.

Якщо функція приймає чи повертає календарний день — тип `DateISO`.

### Баланс рахунку не зберігається колонкою

`account_balances` — це view над `initial_balance` та проведеними
транзакціями. Саме тому подвійне списання неможливе: немає лічильника,
який можна інкрементувати двічі.

**Не додавайте колонку `balance` в `accounts`.** Якщо здається, що потрібен
кеш — спершу виміряйте; на персональних обсягах view швидший за ризик
розсинхрону.

### Захист від дублювання живе в схемі, а не в коді

Три унікальні індекси в `db/migrations/0001_init.ts`:

- `transactions_recurrence_unique` — одне матеріалізоване повторення на
  пару (правило, дата серії);
- `loan_payments_schedule_unique` — один плановий платіж на рядок графіка;
- `loan_payments_transaction_unique` — одна транзакція на виплату.

Ці індекси — причина, чому подвійне натискання кнопки нічого не ламає.
`api/_lib/http.ts` перекладає порушення цих індексів у зрозумілі
повідомлення. Не замінюйте їх перевірками в застосунку.

### Імпорти пишуться з розширенням `.js`, навіть коли файл `.ts`

Це канонічний для TypeScript+ESM запис: `from './money.js'` вказує на
`money.ts`. TypeScript, Vite і Vitest мапують його самі.

Писати `.ts` не можна. Vercel компілює функцію в `.js`, але специфікатор
лишає як є, і Node ESM у проді падає з `ERR_MODULE_NOT_FOUND` — локально
й у тестах при цьому все зелене. Саме тому `allowImportingTsExtensions`
у `tsconfig.json` вимкнений: він дозволяв писати `.ts` і ховав проблему
до самого розгортання.

### У `api/` немає псевдонімів шляхів

`@core/...` і `@/...` працюють у Vite й Vitest, але **Vercel їх не
розв'язує** — з тієї самої причини, що й `.ts`: специфікатор лишається
як написано. У коді функції шлях до ядра тільки відносний:

```ts
import { toNumeric } from '../../src/core/money.js';   // так
import { toNumeric } from '@core/money.js';            // прод ляже
```

Це вже один раз поклало живий застосунок цілком: роутер імпортує всі
маршрути при старті, тож непридатний імпорт в одному модулі вбиває кожен
запит до API, а не лише свій маршрут.

Обидва правила стережуть тести в `tests/imports.test.ts` — вони читають
вихідні тексти, бо жоден звичайний тест цього не спіймає.

### RLS вимагає ролі `app_rls`

`asUser()` виконує `SET LOCAL ROLE app_rls` **перед** `set_config`. Без
цього політики мовчки не діють: роль-власник у Neon має `BYPASSRLS`, і
навіть `FORCE ROW LEVEL SECURITY` її не стосується.

`asSystem()` працює під роллю-власником і призначений **лише** для
таблиці `users` (автентифікація). Не використовуйте його для даних
користувача.

## 2. Де що лежить

| Шлях | Призначення | Залежності |
| --- | --- | --- |
| `src/core/` | Фінансовий рушій | жодних — ні React, ні БД, ні мережі |
| `src/lib/` | Клієнтська інфраструктура: API, стан, теми, форматування | React |
| `src/components/` | Перевикористовувані елементи інтерфейсу | React |
| `src/screens/` | Екрани, по одному на маршрут | React |
| `api/_lib/` | Роутер, автентифікація, доступ до БД, маршрути | Node |
| `api/index.ts` | Єдина точка входу Vercel | — |
| `db/migrations/` | SQL, застосовується по порядку імен | — |
| `tests/` | Vitest: ядро + інтеграція через PGlite | — |
| `e2e/` | Playwright | — |

**`src/core/` не має права імпортувати нічого з решти проєкту.** Це те, що
робить фінансову логіку тестованою й однаковою на клієнті та сервері.

## 3. Як додати зміну

### Нове поле в сутності

1. Міграція **новим модулем** `db/migrations/000N_опис.ts`, доданим у
   `db/migrations/index.ts`. Саме модулем, не `.sql`: у прод потрапляє лише
   те, що є в графі імпортів. Наявні файли
   не редагуються — вони вже застосовані.
2. Тип у `src/core/types.ts`.
3. Мапер у `api/_lib/mappers.ts`.
4. Схема валідації в `api/_lib/schemas.ts`.
5. Маршрут у `api/_lib/routes/`.
6. Інтерфейс.

### Новий маршрут API

Реєструється викликом `open()` або `guarded()` у модулі всередині
`api/_lib/routes/`, а сам модуль додається до списку в
`api/_lib/router.ts`. `guarded()` дає `ctx.userId` і вимагає сесію.

### Нова логіка розрахунків

Тільки в `src/core/`, тільки чистою функцією, тільки з тестом. Якщо
розрахунок потрібен і на сервері — імпортуйте той самий модуль
(`api/_lib/routes/loans.ts` так і робить).

## 4. Перевірка перед комітом

```bash
npm run typecheck   # має бути порожньо
npm test            # 163 тести
npm run build
npm run test:e2e    # потребує CHROMIUM_PATH у контейнерах без браузера
```

E2E піднімає сервер із PostgreSQL у пам'яті — зовнішня база не потрібна й
не постраждає.

## 5. Чого не робити

- **Не змішувати валюти без курсу.** `toBase()` повертає `null`, коли курсу
  немає, і це навмисно. Показати «курс не задано» чесніше, ніж скласти
  долари з гривнями як рівні.
- **Не вважати функцію готовою, бо компонент відмалювався.** Перевіряйте
  поведінку: що саме записалося в базу і як змінився баланс.
- **Не писати у звіті про зроблене те, чого не перевіряли.**
- **Не додавати залежність заради однієї функції.** Форматування дат,
  JWT і хешування паролів зроблені на стандартній бібліотеці свідомо.
- **Не редагувати застосовані міграції.**
- **Не комітити `.env`** та будь-які секрети.
- **Не тягнути бібліотеку іконок цілком.** `src/components/Icon.tsx`
  містить явний реєстр; `import * as icons` додавав у бандл понад 600 КБ.

## 7. Підключення банку

### Баланс після синхронізації коригується по-різному

Банк віддає готовий залишок, а наш баланс — похідна від історії.
Рівність тримається двома різними правилами, і плутати їх не можна:

- **довантаження історії** додало операції на суму D → `initial_balance`
  зменшується на D. Ці операції вже враховані в залишку банку;
- **операція з вебхука** — поправки НЕ робимо. Вона щойно сталася, залишок
  банку зрушив разом із нашим.

### Дублікати ловить `external_id`, а не зміст

Часткові унікальні індекси на `(user_id, external_id)` у `accounts` і
`transactions`. Операції, створені вручну, лишаються з `NULL` і за
унікальність не конкурують.

Вебхук робить `on conflict do update`: незавершена операція (`hold`)
приходить удруге з уточненою сумою під тим самим id. Довантаження робить
`do nothing` — там повтор означає, що запис уже є.

### Токен банку шифрується, а не хешується

`api/_lib/secrets.ts`, AES-GCM, ключ виводиться з `AUTH_SECRET` через HKDF
з окремим `info`. Токен ніколи не повертається клієнту.

**Зміна `AUTH_SECRET` робить збережені токени нечитабельними** — банк
доведеться підключити заново. Це не втрата даних, але попередити треба.

### Дати з драйвера нормалізуються `toDateISO`

PGlite віддає `DATE` обʼєктом `Date`, node-postgres — рядком. Код, який
очікує лише рядок, зелений у проді й падає в тестах. Нормалізатор —
`toDateISO` в `api/_lib/mappers.ts`.

### Одне з'єднання — один запит за раз

`Conn` у `asUser()`/`asSystem()` — це одне з'єднання. `Promise.all([c.query(…), c.query(…)])`
виглядає як паралелізм, але node-postgres ставить такі виклики в ту саму
чергу: виграшу немає, зате є попередження про клієнта, який уже виконує
запит, а в `pg@9` така поведінка зникне зовсім.

Запити в межах однієї транзакції пишемо послідовними `await`.

### Верхня безпечна зона потребує підкладки, а не лише відступу

На iPhone застосунок оголошений `black-translucent` із `viewport-fit=cover`,
тобто вебв'ю **свідомо** заходить під статусбар — інакше під вирізом була б
порожня смуга чужого кольору.

Відступу `pt-safe` на заголовку для цього мало: він лише опускає контент у
спокої, а при прокручуванні той іде просто під годинник. Тому в `App.tsx`
є фіксована смуга заввишки `env(safe-area-inset-top)`. На пристроях без
вирізу її висота нульова.

Її колір — **рівно `bg-canvas`, без розмиття**. Спершу вона була зроблена
як нижня навігація (`bg-surface` + блюр), і на темній темі це не кидалося
в око, а на світлій дало білу пляму поверх сірого фону. Підкладка не є
елементом інтерфейсу — вона має бути невидимою.

### Нижня навігація має нативні розміри

49pt вмісту плюс `env(safe-area-inset-bottom)` — рівно як таб-панель iOS,
разом близько 85px. Ці 34px унизу **не можна забирати**: там домашній
індикатор, і система накриє ним усе, що туди намалювати. Але й
симетричний padding у вкладках туди додавати не треба — іконки піднімалися,
і панель виглядала порожньою знизу.
